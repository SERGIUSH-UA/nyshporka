# Чим наш Kraken відрізняється від ванільного

Прогін Скриби/Писаря йде **не на стоковому kraken 7.0.2**, а на ньому з двома
патчами гарячих функцій сегментації. Патчі лежать у цьому репо як звичайні
модулі й накладаються в рантаймі підміною імен — сам пакет у `.venv_kraken`
не редагується (тому `pip install --force-reinstall` їх не змиє, але й не
збереже: без цих файлів прогін просто стане вдвічі повільнішим).

**Сумарний ефект: 32.7 → 14.8 с/стор на воркер, вихід побітово той самий.**
На трьох воркерах — 17.17 → 8.94–9.61 с/стор (контрольний замір без патчів
на тому ж наборі: 309 с проти 161–173 с).

Це не «оптимізація заради оптимізації»: на 1764-кадровій справі різниця —
приблизно 4 години проти 8.

## 1. `gpu_sato.py` — ridge-фільтр на карту

**Що робить:** підмінює `skimage.filters.sato` на реалізацію тією ж
математикою на torch.

**Навіщо:** профіль py-spy живого прогону показав **43% часу сторінки** в
`skimage.filters.sato` (→ `scipy.ndimage.correlate1d`). Kraken кличе його по
baseline-хітмапі, яка щойно вийшла з мережі — тобто вже лежала на карті, і
стягувалась на CPU заради згорток, для яких GPU і створений.

**Чому це не «схожий фільтр»:** 1D-ядра беруться з самого scipy
(`_gaussian_kernel1d`), послідовність застосування повторює
`_hessian_matrix_with_gaussian`. Для 2D формула коротка: `sigma²·max(λmax, 0)`,
максимум по sigmas.

**Ефект:** фільтр окремо ×42–46, сторінка ×1.51 (один воркер 32.7 → 21.5 с).

**Три пастки, які тут враховані:**

- Kraken кличе `sato(bl_map, black_ridges=False, mode='constant')` — саме
  `constant`, а не дефолтний skimage `reflect`. Для sigma ≤ 1 scipy бере
  `truncate=100`, тобто радіус ядра 71 px: тиха підміна режиму зіпсувала б
  смугу в 71 піксель по краю кожної сторінки. Невідомий режим → `raise`,
  ніякого мовчазного фолбека.
- `reflect` у scipy — це `(d c b a | a b c d | d c b a)`, край **повторюється**.
  У torch `F.pad(mode='reflect')` — це scipy'шний `mirror` (край не
  повторюється). Тому дзеркалення зроблено зрізами вручну.
- `truncate` береться від **оригінальної** sigma, а фільтрується
  масштабованою (`sigma/√2`).

## 2. `fast_geom.py` — CPU-геометрія `blla`

Після перенесення sato на GPU профіль перемірено (16 771 семпл): sato впав до
**0.57%**, а **73.8% часу з'їдала CPU-геометрія kraken**, тоді як власне
розпізнавання (LSTM) — лише 17.4%. Патч б'є три найдорожчі функції.

| функція | що було | що стало | ефект |
|---|---|---|---|
| `_calc_roi` | на кожен рядок перебирались **усі** baselines сторінки (`O(рядків²)`, 2–5 тис. shapely-викликів); Python-цикл по сотнях точок | `STRtree` + векторизований `shapely.intersection` та `np.argmin` | ×2.27 |
| `boundary_tracing` | numpy-масив 8×2 на **кожен** піксель контуру | скалярний Python + плоский список | ×10.56 |
| `_rotate` | `np.indices` → `_apply_mat` → `map_coordinates` | при `order=0` інтерполяції немає — прямий розрахунок координат | ×2.3 |

**Що збережено НАВМИСНО** (виглядає як недоліки оригіналу, але від цього
залежить, які пікселі потраплять у кроп рядка):

- порядок додавання суміжних ліній — від нього залежить `unary_union`;
- перший мінімум при рівних відстанях (як у `min(..., key=...)`);
- `np.argmax` на суцільних нулях = 0, а не «не знайдено»;
- `neighbors[idx-1]` при `idx == 0` бере **останній** сусід;
- мертва гілка `if t == 'Point'`, що порівнює геометрію з рядком і ніколи не
  істинна — не «полагоджена».

**Три пастки, знайдені пробою, а не з документації:**

- у `warp_nearest` округлення `floor(x + 0.5)` (round-half-up), а **не**
  `np.round` — той банкірський (0.5 → 0, 2.5 → 2) і давав би інші пікселі;
- межі перевіряються **після** округлення: координата −0.4 законно дає крайовий
  піксель, а не `cval`. Перша версія перевіряла до округлення й розходилась на
  2.6% пікселів — усі рівно по краю патча;
- фолбек у `rotate_fast` кличе `kseg._rotate_orig`, а не імпортує `_rotate`:
  після `install()` друге ім'я вказує вже на саму заміну → нескінченна рекурсія.

## 3. Як увімкнено

Обидва — **дефолт ON у самому раннері** (`nyshporka.htr.runner`,
`--fast-geom / --no-fast-geom`, `--gpu-sato / --no-gpu-sato`); `gpu_sato`
реально ставиться лише на `cuda`. Консоль передає **тільки вимкнення**
(`gpu_sato: false` / `fast_geom: false` у cfg job'а).

> 🔴 До 2026-07-30 було навпаки: у CLI `store_true` (тобто OFF), а `True`
> ставила лише консоль. Ручний запуск скрипта мовчки їхав старим шляхом —
> 30–43 с/стор і `nvidia-smi` util 0% при повній VRAM, що виглядало як зламана
> карта. Саме на це напоровся прогін ф.792-1-43.

Вимкнення тепер друкується в шапку логу (`⚠ sato НА CPU`), бо різниця вдвічі, і
найдешевший спосіб її діагностувати — побачити причину в перших рядках.

## 4. Як не втратити це при оновленні

Патчі підмінюють **приватні** функції чужої бібліотеки. Небезпека не в тому, що
вони впадуть — впаде голосно, а в тому, що нова версія kraken змінить семантику
й розбіжність буде **тихою**: той самий скан дасть інші полігони рядків, тобто
інший текст, без жодної помилки.

Захист у три шари:

1. **Пін** `kraken==7.0.2` у маніфесті рушіїв (`htr/data/engines.yaml`).
   Раніше стояло просто `kraken` — перевстановлення середовища через півроку
   привело б іншу версію.
2. **Гард версій у рантаймі:** `fast_geom.install()` звіряє kraken і shapely,
   `install_gpu_sato()` — scikit-image і scipy; розбіжність → гучне
   попередження з командою перезвірки. `install()` додатково перевіряє, що всі
   три підмінювані імена в модулі ще існують.
3. **Верифікатори** — вони і є доказ, а не заява:

```
<інтерпретатор рушіїв> -m nyshporka.htr.patches.gpu_sato_verify
<інтерпретатор рушіїв> -m nyshporka.htr.patches.fast_geom_verify 5
```

Обидва ганяють стару й нову версії **пліч-о-пліч на живій сегментації** реальних
сторінок і звіряють самі масиви, а не «схожість». Синтетика тут нічого не довела б:
`_calc_roi` чутлива до взаємного розміщення рядків, тобто до конкретної сторінки.

**Досягнуті результати звірки:**

- `gpu_sato`: max |Δ| **1.2e-07** при діапазоні значень 0.31, IoU маски
  1.000000, кореляція 1.00000000; текст **18/18 сторінок ідентичний**, conf
  збігається до 4-го знака.
- `fast_geom`: **82/82** `_calc_roi` (максимальне відхилення 0 px), **98/98**
  `boundary_tracing`, **164/164** `_rotate`, наскрізно **6/6 сторінок** з
  ідентичним текстом і conf.

Версії, на яких це доведено (константи `TESTED_*` у самих модулях):

```
kraken==7.0.2   scikit-image==0.25.2   shapely==2.1.2
scipy==1.15.3   torch==2.13.0+cu126    numpy==2.4.4
```

## 5. Що НЕ варто чіпати

- **DP-цикл `_calc_seam`** (10.8% часу): заміна `as_strided` на прямі зрізи дала
  5.6 мс проти 5.0 — оригінал уже оптимальний. Цикл послідовний, GPU не поможе;
  єдиний шлях — numba/Cython, яких у `.venv_kraken` немає.
- **`autocast=True`**: на h1800 дає **0 рядків** (fp16 тихо ламає сегментацію).
- **YOLO замість `blla`**: не пряма заміна. `blla` віддає baseline + polygon, і
  `rpred` по baseline робить dewarping; axis-aligned bbox на похилому рукописному
  рядку захопить сусідні, а розпрямляти буде нічим.
- **`--seg-height 1440`**: пік VRAM 3876 → 2718 МБ і 8.94 → 7.56 с/стор, але
  **−11% слів на fuzzy-порозі 80**. Для пошуку роду неприйнятно.

Пов'язана пам'ять: `htr-kraken-cpu-bound-not-gpu`.
