# Читання справи на чужій машині

**Вхід** — тека кадрів і машина, до якої є доступ по SSH. **Вихід** — текст у
теці прогону, число сторінок із текстом = число кадрів, справа видима в обліку,
машина відпущена.

🔴 **Головне: «хмара» тут не означає «потужніша карта».** Найдорожче в сторінці
рахує процесор — близько трьох чвертей часу йде на геометрію рядків. Тому
єдина причина везти справу кудись — там **більше ядер**. Відеопам'ять не
прискорює нічого, вона лише обмежує, скільки процесів улізе поруч.

Наслідок, який економить найбільше: **малу справу везти нікуди не треба.**
Холодний старт чужої машини коштує близько восьми хвилин незалежно від обсягу —
на сотні кадрів весь захід і буде цими вісьма хвилинами.

---

## Крок 0 — план, який нічого не коштує

```bash
nysh cloud plan <тека> --host <машина>
```

Жодної мережевої дії. Показує кадри, обсяг, письмо, модель, шифру, скільки
процесів дасть машина, що саме їх обмежує, скільки годин і грошей.

**Приймач:** у плані названо шифру справи. Без неї прогін ляже «нічиїм» — текст
буде, а до якої справи належить, невідомо.

🔴 **Письмо мусить бути визначене.** Якщо план каже «не визначається» —
подивіться перший скан оком і вкажіть `--script cyrillic` або `--script latin`.
Вгадувати не можна: невідповідність рушія письму **не дає збою** — текст
виходить, впевненість не падає, і виглядає це як погані скани.

## Крок 1 — машина, один раз

```bash
nysh cloud hosts add <ім'я> <user@host[:порт]> --key ~/.ssh/id_ed25519
nysh cloud prepare <ім'я>
```

`prepare` збирає середовище рушіїв на машині. Робиться **один раз на машину**,
повторний виклик безпечний.

🔴 **Ключ записується шляхом, ніколи не вмістом і не паролем.** Файл машин
лежить у теці простору, яку кладуть у git і в хмарну синхронізацію.

**Велика справа — налаштуйте сховище.** Передача напряму впирається не в смугу,
а в кількість файлів; десятки гігабайтів так їдуть годинами:

```bash
nysh cloud hosts storage <сегмент> --endpoint <адреса>
# ключі — тільки в середовищі: NYSHPORKA_S3_KEY / NYSHPORKA_S3_SECRET
```

План скаже число: «заливка займе N год». Це і є підстава вирішувати.

---

## Крок 2 — запуск

```bash
nysh cloud start <тека> --host <машина> --script cyrillic
```

Команда **повертається одразу**: робота лишається жити на машині окремо від
вашого з'єднання. Закритий ноутбук, обрив каналу й Ctrl+C її не вбивають.

🔴 **Після обриву правильна дія — повторити ту саму команду.** `start` знайде
свою живу роботу й підхопить її. Другої машини він не візьме — саме на цьому
тримається весь захід.

⚠ Скільки процесів — вирішує **виміряне** залізо, не заявлене. Машина може
показувати 192 ядра там, де ваша частка — 48; план бере меншу з двох цифр.
Задати своє число можна (`--shards N`), але лише **менше** фізичного: щільна
книга справді потребує менше процесів, а більше — не сповільнює прогін, а
завалює його.

---

## Крок 3 — стеження

```bash
nysh cloud state           # або: nysh cloud state <захід>
```

Числа беруться з **диска машини**, а не з лога. Рядок «готово» в лозі доказом
не є: лог пише процес, а сторінки лежать окремо, і розходяться вони саме тоді,
коли щось пішло не так.

Опитувати частіше ніж раз на кілька хвилин немає сенсу.

---

## Крок 4 — забрати й звірити

```bash
nysh cloud fetch
nysh cloud verify
```

🔴 **Це два кроки, а не один, і між ними нічого не можна пропускати.**

`verify` зводить три незалежні знаменники — кадри в теці, число з мети прогону,
тексти на диску — і звіряє **покадрово**: той самий кадр ↔ той самий текст, а не
«однаково штук». Плюс карантин: сторінка, яку прогін відклав, **не є
прочитаною**, хоч би скільки текстів лежало поруч.

Що робити з неповним:

* **хвіст малий** (до ~2% і в будь-якому разі до ~сотні сторінок) — доганяйте
  **вдома**: `nysh read <тека>`. Друга оренда заради двадцяти сторінок — це
  плата за вісім хвилин підготовки, а не за роботу;
* **бракує багато** — машину ще не гасіть: недороблене лежить на ній.

---

## Крок 5 — відпустити машину

```bash
nysh cloud stop
```

🔴 **Відмовиться, поки роботу не звірено, — і це правильно.** Забрати й
погасити виглядає як одна дія, але між ними лежить єдина точка, у якій ще можна
врятувати роботу. Кинути захід свідомо можна через `--force`; мовчазного шляху
туди немає.

⚠ Якщо машина орендована — **лічильник іде до знищення інстансу**, а не до
кінця роботи. `nysh cloud state --all` показує заходи, які ще тримають машину.

## Коли щось пішло не так

| що видно | що це насправді |
|---|---|
| прогін «успішний», а сторінок менше | код повернення повноти не доводить: є клас відмов, за якого лог обривається, перелік збоїв порожній, а процес виходить нулем |
| привезено менше, ніж читалось | звірка **покадрова**: однакове число текстів ще не означає ті самі сторінки |
| «повністю», а на диску не все | карантин переживає перезапуск, і другий захід відкладених сторінок не бере |
| пошук по декоду дає нуль без помилки | голоси склались в одну теку й перетерли один одного; вони мусять лежати сестринськими теками `<прогін>-<тег>` |
| машина «не відповідає» одразу після старту | щойно піднятий бокс кілька хвилин не приймає з'єднань — це не привід брати другий |
| заливка йде годинами | канал упирається в кількість файлів, а не в смугу: налаштуйте об'єктне сховище |

---

## Чого тут немає навмисно

**Автоматичних рішень.** Ніщо не переорендовує машину, не гасить її за
таймаутом і не доганяє хвіст саме. Це рівно той контур, у якому помилка коштує
або грошей, або роботи, — тож рішення лишаються людині.

**Оренди на ринку.** Вбудований бекенд працює з машиною, яку ви **вже маєте**.
Оренда додається окремим пакетом-плагіном; `nysh cloud hosts` показує, які
бекенди є і які не завантажились.
