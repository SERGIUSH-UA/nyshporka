# Читання справи: від теки кадрів до повного декоду

**Вхід** — тека сканів або PDF. **Вихід** — текст у теці прогону, число сторінок
із текстом = число кадрів, справа видима в обліку. Читати на чужій чи
орендованій машині — скіл `run-case-remote`.

🔴 **Головне, що визначає всі рішення нижче: це не задача для відеокарти.**
Більшу частину часу сторінки рахує процесор (геометрія рядків, нарізка); карта
зайнята коротко. Тому ручка — **ядра**, а пам'ять карти лише обмежує, скільки
процесів можна пустити поруч. Порада «докупити карту» тут найгірша.

Обидва ліміти передбачувані наперед:

* **пам'ять задає пропорція кадру**, а не тип документа, роздільність скану чи
  число рядків (крок 2);
* **час задають рядки**: стала на сторінку (мережа сегментації) плюс рядки ×
  ціна рядка, і довші рядки дорожчі. Тип документа впливає лише через
  щільність письма.

Ще два правила, від яких залежить, чи прогін узагалі дійде до кінця:
`--shard` без спільного `--gpu-lock` не сповільнює прогін, а **завалює** його
(крок 2); приймач повноти — **диск**, а не код повернення (крок 4).

Повне обґрунтування з замірами — `references/htr-tuning.md` поруч із цим файлом.

---

## Крок 0 — подивитись на матеріал, перш ніж запускати

```bash
nysh case                      # що це за тека: скільки кадрів, одна справа чи багато
nysh doctor                    # чи є рушій, місце, карта
```

Справа на сотні аркушів читається годинами, тож помилка на старті коштує не
хвилин. Питання, на які треба мати відповідь **до** запуску: скільки кадрів,
яке письмо (кирилиця чи латинка), чи це взагалі одна справа.

**Приймач:** `nysh case` назвав шифру. Немає шифри — прогін ляже «нічиїм», і
знайти його потім можна буде лише за іменем теки.

## Крок 1 — розвідка на частині, а не на всій справі

```bash
nysh read <тека> --limit 20
```

Двадцять сторінок кажуть те, чого не скаже жоден план: чи бере рушій це письмо,
чи не розсипається сегментація на цьому формулярі, скільки насправді йде
сторінка на **цій** машині.

**Приймач:** у виході є текст, у якому впізнаються слова. Порожньо або суцільний
шум — далі не гнати, спершу розібратись із матеріалом (перекошені кадри, надто
малий масштаб, вицвіле чорнило).

## Крок 2 — скільки процесів пустити

**Вирішує вільна пам'ять карти, а не кількість ядер.** Щойно сумарно
впираєшся у стелю, драйвер починає перекладати пам'ять через шину — і прогін не
сповільнюється, а **завалюється**. Рахується наперед:

* кожен шард із двома голосами постійно тримає **~1.2–1.9 ГБ** (ваги й буфери);
* поверх них карта тримає **один** пік сегментації (вона йде під локом):
  **~0.1 ГБ + 0.5 ГБ × Мп входу сегментатора**, де вхід = 1800² × ширина/висота
  кадру. Портрет (0.75) — ~1.3 ГБ, розворот (1.3) — ~2.2 ГБ;
* шардів = ⌊(пам'ять карти − пік найширшого кадру) / зайнятість шарда⌋.

Кадр ширший за 2.5:1 (етикетка плівки, корінець) раннер сам стискає до 8 Мп
входу (`--seg-max-mpx`, позначка `seg_capped` у меті): одна така аномалія не
мусить диктувати пам'ять на всю справу. Фактичний пік кожної сторінки —
`vram_peak_mb` у меті.

```bash
# три процеси, спільний лок, sato знято з карти
nysh read <тека> --shard 1/3 --gpu-lock <файл> --no-gpu-sato
nysh read <тека> --shard 2/3 --gpu-lock <файл> --no-gpu-sato
nysh read <тека> --shard 3/3 --gpu-lock <файл> --no-gpu-sato
```

🔴 **`--shard` без спільного `--gpu-lock` — найпоширеніша помилка.** Два
одночасні проходи сегментації не влазять у пам'ять типової карти. Лок мусить
бути **один і той самий файл** для всіх шардів.

⚠ Виграш дає не шардинг сам собою, а шардинг **разом зі знятим sato з карти**:
інакше найдорожча фаза йде під локом, і процеси стають у чергу замість
паралельної роботи. `--no-gpu-sato` результату не міняє — лише спосіб рахунку.

**Приймач — симптом, а не секунди.** Пам'ять карти під стелею при простої
процесора означає буксування: знімай шард. Здорове завантаження виглядає
інакше — процесор зайнятий.

⚠ **Секунди на сторінку на робочій машині нічого не доводять**: той самий прогін
дає різницю в рази залежно від того, що крутиться поруч. Порівнювати режими по
часу тут не вийде.

## Крок 3 — повний прогін

Число шардів від типу документа не залежить: щільний формуляр читається
довше, але пам'яті бере стільки ж, скільки рідкий аркуш тієї самої пропорції.
Шарди резюмуються спільно, тож зняти зайвий можна будь-коли без утрат — а от
додати після падіння коштує часу.

⏱ Де йде час сторінки — `stages` у меті (`seg_net`, `sato`, `polygon`,
`segment`, `recognize`, `other`), без профайлера. Міряючи сегментацію, став
`--no-seg-cache`: сторінки з кешу її не проходять.

## Кілька справ поспіль — чергою

Свій цикл навколо `nysh read` не потрібен:

```bash
nysh queue add DAHMO/315/8433 data/raw/dahmo_315/spr-8434   # ключ із реєстру опису або тека
nysh queue run            # вести чергу; одну справу й вийти — --stop-after-case
nysh queue                # що на якому етапі, що лишилось, чому стоїть
```

Справа проходить кадри → паспорт → каталог → пул → читання → облік → віддача;
що зроблено, черга бере з диска, тож після `Ctrl+C` чи вимкненої машини той
самий `nysh queue run` продовжує й прочитаного не перечитує. Зупинити після
поточної справи — `nysh queue stop` з іншого термінала.

🔴 Справу зі станом «чекає вас» не обходь: у рядку є причина й команда.
Шифру, письмо справи й рішення «прийняти неповне читання уривком»
(`nysh queue set <справа> --partial "чому"`) дає людина. Розвідку на частині
(крок 1) і число процесів (крок 2) роби до черги; процеси для справи —
`nysh queue add … --workers N`.

## Крок 4 — приймач повноти по диску

```bash
nysh cases           # «сторінок з текстом: N з M» для цієї справи
```

🔴 **Код повернення повноти не доводить.** Є клас відмов, за якого сторінка
вбиває процес: лог обривається, перелік збоїв порожній, прогін «успішний».
Рахувати треба **файли на диску**.

⚠ Для часткового прогону (`--limit`, `--pages`, `--shard`) повнота не міряється:
ти прочитав менше навмисно.

**Приймач:** N = M. Менше — перезапустити прогін; він продовжить із того, що вже
прочитано, а не почне спочатку.

### Перечитати справу

🔴 **Раннер у теці з текстом доганяє, а не перечитує.** Сторінку з готовим
текстом він пропускає, тож та сама команда в ту саму теку не перечитає нічого.
План каже це сам: `nothing_to_read` (усе вже має текст), `catch_up` (дочитає
решту), `catch_up_mixed` (решту дочитає інша модель — корпус буде змішаний).

- **Дочитати сторінки без тексту** — та сама команда; на прочитаній цією
  моделлю справі — з `--rerun` (він лише знімає відмову «уже прочитано»).
- **Перечитати все** — окрема тека `--out <тека>` або інша модель `--model`.
  У ту саму теку — ніколи: текст двох прочитань змішався б.
- Хмарний `nysh cloud go … --rerun` справді читає наново: привезений текст на
  машину не їде.

## Крок 5 — записати, що зроблено

Прогін, який не потрапив в облік, для наступної сесії не існує: вона
перечитає ту саму справу. Облік — скіл `keep-records`.

## Коли якість не влаштовує

| симптом | важіль | ціна |
|---|---|---|
| рядки злипаються, сегментація рве | `--seg-height` менше | 🔴 **коштує прочитаним**: 1440 ≈ −4% слів, 1200 ≈ −10% відгуку на довгих словах |
| вицвіле чорнило, блідий скан | контраст (див. доку) | безпечно |
| формуляр на 200+ рядків | стеля кінців скелета `--max-endpoints` (типово 400) | сторінку, яку стеля різала, раннер сам перепускає з `--ceiling-retry` (1600); вручну піднімати не треба |
| треба швидше, точність не критична | `--one-voice` | сліпіше: другий рушій помиляється інакше й витягує те, де перший підставив правдоподібне слово |
| PDF-справа (фото з телефона), 3–9 рядків на сторінку замість десятків | нічого вручну: кадри лежать боком, бо їх розгорнула версія до 0.27. План читання лише називає їх (`pdf_sideways`) і нічого не змінює; запуск читання спершу відкладає прочитане з них у `_bokom/` прогону, потім розгортає кадри й дочитує саме ці сторінки | безпечно; кеш сегментації цих сторінок знято, тож вони сегментуються наново |
| письмо мішане: кирилиця з латинськими вставками чи аркушами | `--with latin` | латинська модель стає третім голосом того самого проходу, вихід у `<прогін>-<тег>`; сегментація рахується раз, тож другий прогін не потрібен. Лише для кириличного прогону — у латинської справи основа інша, і там це окремий `--model` |

🔴 `--seg-height` не вмикається саме собою і **вмикається свідомо**: скажи
людині, що ти його поставив. Інакше згодом «прізвище не знайшлось» припишуть
моделі, а не цьому прапорцю.

## Прискорення, які вже увімкнені

Раннер латає kraken і skimage (`fast_geom`, `fast_order`, `fast_seam`,
`seg_resize`, `gpu_sato`, `fast_clahe`): кожен патч дає результат до біта як в
оригіналі, увімкнений за замовчуванням і має вимикач `--no-…`. Патчі швів і
CLAHE на неперевіреній версії бібліотеки вимикаються самі й кажуть про це в
лозі. Опис і верифікатори — `htr/patches/README.md` пакета.

Писар (PARSeq) іде у fp16 сам лише на картах із тензорними ядрами
(`--pysar-fp16 auto`). На старих картах без них fp16 повільніший за fp32, тож
`on` там не ставити.
